# Review Probes

Select probes from the guarantees and paths identified in the impact trace. Use the change signals to look for hidden consumers and test conditions. Group consumers when the same boundary preserves the same guarantee for them.

| Change signal | Follow this path | Seek evidence that distinguishes success from failure |
| --- | --- | --- |
| New behavior, branch, or fallback | Request or command through dispatch to the selected implementation and the caller-visible result | Check acceptance conditions and defaults. Exercise empty, missing, invalid, and limit cases where accepted by the interface. Check for stub, no-op, constant return, swallowed errors, ignored inputs, unintended order dependence, or success before work finishes. |
| State, ownership, or lifecycle | Creation, publication, mutation, cancellation, shutdown, and release, including callbacks and suspension points | Check isolation, atomicity, lifetime, reentrancy, ordering, bounded waits, and failure or cancellation propagation. Exercise a competing operation or injected failure at the state transition that can break the invariant. |
| Persistence or distributed effects | Old and new records through read and write paths, transaction boundaries, and retries | Check partial writes, rollback and reversibility, duplicate delivery, idempotency, interrupted recovery, and migration with existing data. Use a production-shaped store or fixture and confirm persisted state after failure. |
| Events, background work, or shared resources | Producers, routing, subscribers, workers, and competing users of the same cache, queue, or quota | Check ordering, duplicates, delayed processing, invalidation, resource isolation, and effects on features with separate entry points. |
| Public interface, dependency, or removal | Existing callers through source, binary, wire, schema, or persisted-data compatibility boundaries | Check old and new versions where supported, versioned compatibility contracts, implicit defaults, error semantics, and callers that receive deprecated or unknown values. |
| Trust boundary or user data | Route, identity, permission, tenant, validation, and all observable outputs | Check deny behavior with harmless local fixtures and confirm the boundary is enforced for each real entry point. Check exposure in logs, errors, cache keys, exports, and stored results. |
| Configuration, platform, or packaging | Effective defaults, build flags, adapters, startup, and shipped artifact | Confirm affected configurations select the intended implementation. Exercise changed gates and backend-specific paths. Verify shipped assets or generated outputs when the source alone cannot establish behavior. |
| Hot path or resource budget | Representative input through the full operation, including I/O, synchronization, and cleanup | Compare the same conditions for old and new behavior. Measure the relevant latency, memory, allocations, throughput, or contention when the contract depends on it. Check upper bounds on realistic worst cases. |
| Responsibility or dependency changes | Source of truth, owner, consumers, and dependencies across module boundaries | Trace competing decisions, duplicated policy, or weakened isolation to a concrete inconsistency or violated contract. Verify that a single owner still governs the behavior. |
| User-facing flow | Actual interaction through loading, empty, error, cancellation, and recovery states as applicable | Check that controls, focus, navigation, and accessibility state reflect what the user can do and what the application actually completed. |
| Test or verification changes | Fixture, dispatch, assertion, target selection, and build or CI entry point | Show that the test would fail on the contract violation it claims to guard. Check removal of assertions, weakened invariant or verification coverage, mock substitution, skipped configurations, nondeterminism, and setup that masks cold start or old data. |
