# Structurizr rules for the Invar C1/C2 Map

Use standard Structurizr DSL syntax within the following Map profile. These restrictions define what Invar emits and Explorer can depict. [Structurizr language reference](https://docs.structurizr.com/dsl/language)

| Decision | Rule |
|---|---|
| Root | Write a complete UTF-8 `workspace` in the root `ARCHITECTURE.dsl`. Put `!impliedRelationships false` before the single `model` block. Use one statement per line, an opening brace on the declaration line and a closing brace on its own line. |
| C1 scope | Show the subject as a `softwareSystem`, the people and external systems interacting with it, and the purpose of each interaction. Attribute external roles and ownership to a requirement or explicit binding. |
| C2 scope | Put each runtime application or owned data store inside its owning `softwareSystem` as a `container`. Decide from runtime responsibility and ownership. Packages own declarations; a package, an in-process library or a payload alone does not establish a container. An independently owned storage service belongs outside the subject. |
| Areas | Place every top-level `person` and `softwareSystem` immediately inside exactly one model-level `group` with a unique, nonblank domain name. Reuse a domain by placing members in that group. Containers inherit the owner's domain. Establish both memberships before declaring a cross-domain edge. Keep uncertain ownership explicit. |
| Identity | Assign each element one globally unique flat identifier matching `[A-Za-z_][A-Za-z0-9_]*`. Preserve it through display-name and layout changes. Use a nonblank display name and describe the element's responsibility. |
| Connections | After declaring both endpoints, write the edge at model scope as `sourceId -> targetId "operation"`, appending a quoted technology only when known. Use distinct element IDs and a nonblank verb phrase that describes what the source does to the target. Groups cannot be endpoints. Emit system-level and container-level operations explicitly at their respective scopes. Isolated elements are valid. |
| Ownership across packages | Declare elements at their owning scope. Place a cross-boundary relationship in the nearest common enclosing scope of the two owners, where its source, destination and operation can be read together. A single root can express these scopes. If the repository already splits the model, retain local declarations and validate the assembled workspace; splitting or adding includes is optional. |
| Evidence | Immediately before each element and edge, write one or more `// Source: <repo-relative-path>:<one-based-line> sha256=<lowercase SHA-256 of the file bytes>` comments. Cite reviewed requirements and design for intended topology. Cite the concrete production call and effective bindings for implemented runtime claims. Keep credentials and secret values out of descriptions and citations. |
| Views | Supply the model alone, or one `systemContext` view and one `container` view for the same declared subject. Give the views distinct keys and place only `include *` inside each. |
| Presentation | Use semantic roles and, where supported by evidence, a role tag such as `database`, `queue`, `worker` or `website`. Explorer owns placement, paths, ports, shapes and styling. C3/C4 code structure belongs to the source index. |
