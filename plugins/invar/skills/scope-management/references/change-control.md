# Change Control

A scope expansion requires authorization from the user or a documented authority holder, not from the agent or this skill.

1. Freeze the affected proposed edit, leaving independent authorized work available.
2. Obtain SA evidence: proposed change, why current boundary is insufficient, alternatives, consequences and unknowns.
3. If behavior, acceptance criteria, or obligations change, route to RE through the caller for a proposed Requirements Baseline revision and semantic validation.
4. Present the decision and trade-offs to the authority holder. Record explicit authorization and its limits; silence is not approval. If rejected, retain the old baseline; if blocked, report the affected work as blocked.
5. Once authorized, RE updates the requirements baseline if needed. Request SA reanalysis of affected boundary/impact and checks. SM creates the next Scope Baseline revision linked to the new inputs and authorization. Mark old baseline superseded; resume affected work only when active.

Necessary supporting changes within existing authorized behavior and constraints require rationale, not repeated stakeholder approval. Do not disguise expansion as cleanup or refactoring. See [shared contract](../../../references/requirements-and-scope.md).
